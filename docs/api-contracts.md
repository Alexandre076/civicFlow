# API contracts — v1 (planned)

Design baseline for [Issue #18](https://github.com/Alexandre076/civicFlow/issues/18)
and [Epic #2](https://github.com/Alexandre076/civicFlow/issues/2), consumed by
#19–#26. These contracts are not implemented. Today only `GET /health` exists;
see [architecture](architecture.md), [authentication](authentication.md) and
[streaming](streaming.md). Epic #2 uses PostgreSQL and deterministic mock replies;
LangGraph belongs to Epic #3 and municipal protocols/tools to Epic #4.

## Routing and compatibility

New application routes use `/v1` relative to the configured API base. Examples
below omit that prefix in tables: `/conversations` means `/v1/conversations` on
FastAPI, or `/api/v1/conversations` through the existing Vite proxy. The proxy
strips only `/api`; `/health` remains unversioned. Prefer same-origin browser
requests with credentials. Production ingress is still an open deployment choice.
Breaking payload/behavior changes require a new major path version. Additive
optional fields are compatible; clients ignore unknown object fields. New status
or event variants require coordinated client support before deployment.
JSON uses snake_case, UTF-8, RFC 3339 UTC timestamps and opaque string IDs;
example prefixes are illustrative, never authorization evidence. Bodies reject
unknown writable fields; clients cannot assign owners, roles, statuses or IDs.
Authenticated JSON/history responses use `Cache-Control: no-store`.

## Endpoints

All routes except login/callback require a valid BFF session. Every mutation
requires the CSRF header described in [authentication](authentication.md).

| Method | Route | Request | Success |
| --- | --- | --- | --- |
| GET | `/auth/google/login` | Optional `return_to` and supported `locale` | 302 Google redirect |
| GET | `/auth/google/callback` | OIDC `code`, `state` or provider error | 303 allowed UI destination; session cookie |
| GET | `/auth/me` | None | 200 User; `X-CSRF-Token` response header |
| POST | `/auth/logout` | No body | 204; revoke session and expire cookie |
| PATCH | `/users/me/preferences` | `{"preferred_locale":"en"}` | 200 updated User |
| POST | `/conversations` | `{}` | 201 Conversation; `Location` API resource URL |
| GET | `/conversations` | `limit`, `cursor` | 200 ConversationPage |
| GET | `/conversations/{id}` | None | 200 Conversation (no embedded messages) |
| GET | `/conversations/{id}/messages` | `limit`, `cursor` | 200 MessagePage |
| DELETE | `/conversations/{id}` | No body | 204; inaccessible immediately |
| POST | `/conversations/{id}/messages` | SendMessage | 200 SSE; see [streaming](streaming.md) |

Preference PATCH requires the one supported field; other locales return 422.
Conversation creation has no automatic transport retry guarantee: disable repeat
submission and reconcile the list after an uncertain outcome. Message sending
has the stronger idempotency contract below. Resume means retrieve metadata,
paginate history, and send to the same conversation ID; no separate resume route.

## Public schemas and examples

These are wire DTOs, not ORM models. All listed fields are required unless
explicitly nullable. IDs and timestamps are generated by the backend.

**User**: `id`, `display_name` (nullable string), `email` (nullable string),
`preferred_locale` (`pt-BR` or `en`). Profile text is untrusted display data.

```json
{
  "id": "usr_123",
  "display_name": "Alex",
  "email": "alex@example.com",
  "preferred_locale": "pt-BR"
}
```

**Conversation**: `id`, `created_at`, `updated_at`, `last_language` (nullable
BCP 47 tag, server processing metadata). No owner ID is exposed or accepted.
`updated_at` advances on accepted user messages and terminal assistant updates,
not every delta. Default UI titles are localized client labels, not stored text.

```json
{
  "id": "conv_456",
  "created_at": "2026-10-20T16:00:00Z",
  "updated_at": "2026-10-20T16:00:00Z",
  "last_language": null
}
```

**Message**: `id`, `conversation_id`, `sequence` (positive integer, unique and
increasing within a conversation), `role` (`user`/`assistant`), `content` (plain
text), `created_at`, `updated_at`, `status`, `client_message_id`,
`detected_language` (nullable BCP 47 tag), `response_language` (nullable BCP 47
tag), `language_source` (nullable `message`/`conversation`/`ui_preference`),
`error_code` (nullable stable code). `client_message_id` is shared by the user
message and its paired assistant message. User status is always `completed`;
assistant status is `streaming`, `completed`, `interrupted`, `cancelled` or
`failed`. Only completed assistant messages have authoritative final content;
other terminal states retain explicitly marked partial text.

```json
{
  "id": "msg_123",
  "conversation_id": "conv_456",
  "sequence": 1,
  "role": "user",
  "content": "Existe um buraco na minha rua.",
  "created_at": "2026-10-20T16:00:00Z",
  "updated_at": "2026-10-20T16:00:00Z",
  "status": "completed",
  "client_message_id": "client_789",
  "detected_language": "pt-BR",
  "response_language": null,
  "language_source": null,
  "error_code": null
}
```

Assistant metadata records the selected `response_language` and `language_source`;
`detected_language` is null for assistant messages. User messages record detected
language when available; response language/source are null. Language metadata is
set before `message.started`, may be null before processing, and never supplied
by the browser. Terminal errors carry `error_code`; successful messages use null.

**SendMessage** (maximum JSON body 64 KiB):

```json
{"content":"Existe um buraco na minha rua.","client_message_id":"client_789"}
```

`content` must contain non-whitespace text and at most 8,000 Unicode code points;
valid text is stored unchanged. `client_message_id` is a client-generated UUID
or opaque random ASCII identifier of 1–128 characters from `[A-Za-z0-9_-]`.
The example is illustrative; clients should generate at least 128 random bits.
No attachments, owner, role, locale override or provider configuration is accepted.

Persistence requires users, linked identities, sessions, conversations, messages
and durable attempt uniqueness. Internal records include owner foreign keys,
canonical issuer/subject, session secret hashes, attempt fingerprints and stream
leases. Those fields never enter public DTOs. PostgreSQL schema, indexes,
transaction mechanisms, ORM and migrations are implementation work for #20/#21.
There are no incident/protocol records in this epic.

## Complete history and pagination

Use keyset cursors, default `limit=50`, range 1–100. Invalid limits return 422;
invalid, tampered, wrong-user or wrong-resource cursors return 400
`INVALID_CURSOR` without leaking their contents. Cursors are opaque and
integrity-protected, scoped to the user, route, conversation if applicable and
initial high-water mark. Changing page size is allowed.

Messages order by immutable `sequence ASC`; conversation lists order by immutable
`(created_at DESC, id DESC)`, avoiding reordering during streaming. Starting a
pagination traversal captures the highest sequence or conversation key. Follow
`next_cursor` until null to retrieve every surviving record up to that mark.
New records appear on a fresh traversal; updates to existing records show their
latest state. Deletions may shorten pages; this is not a database snapshot.
No permanent recent-only history cutoff. Polling a fresh history traversal also
reconciles terminal statuses after disconnects.

Both page types use this envelope (`items` contains the corresponding DTO):

```json
{"items":[],"next_cursor":null}
```

For example `GET /api/v1/conversations/conv_456/messages?limit=50` returns
`{"items":[...],"next_cursor":"opaque_continuation"}` when more records remain;
request the same route with the URL-encoded cursor. A client deduplicates by ID,
merges by `updated_at` and sorts messages by sequence.

## Ownership and deletion

The session determines the user; every metadata read, page, send/replay and delete
queries the conversation under that owner. Unknown and non-owned IDs both return
404 `CONVERSATION_NOT_FOUND`, including repeated deletes and stale page cursors
for a deleted conversation. Ownership is checked before cursor/attempt details.
Never accept an owner identifier from a request. Child messages and attempts
inherit conversation ownership; possession of any identifier grants no access.

Deletion immediately removes the conversation from navigation and denies all
future reads/writes, including retries. Atomically serialize deletion with send
acceptance and stream writes, revoke active attempts, and stop generation. Workers
must check the deletion fence before any commit; they cannot recreate deleted
rows. If connected, send `message.error` with `CONVERSATION_NOT_FOUND` and close;
otherwise close silently. Clients stop rendering, remove cached history and
return to the list on 404. Deleting a conversation never deletes the user's account.

The user-visible guarantee is immediate logical erasure with no restore in MVP.
Physical cascade deletion versus an inaccessible tombstone pending purge remains
open for #21; tombstones must not retain message content after purge. Raw messages,
attempt records and cached content must be covered by the deletion policy.
Retention duration, purge deadlines, backup expiry, operational logs and privacy
review remain explicit release decisions; no promise of immediate backup erasure.
Document those before storing real citizen reports in a deployed service.

## UI locale and assistant language

UI uses react-i18next/i18next and supports `pt-BR` and `en`. Before login choose
explicit local preference, then first supported browser language, then `pt-BR`.
Map `pt`/`pt-*` to `pt-BR` and `en-*` to `en`; ignore unsupported tags. Missing
translation keys fall back to `pt-BR`. On first account creation, a validated
login `locale` initializes the preference (otherwise `pt-BR`); an existing user's
server preference always wins after login. A signed-in selector PATCHes the
profile and updates local preference only on success; failed saves retain the
previous locale. Never silently overwrite the profile from browser storage.

Assistant language is selected server-side: confidently detected citizen-message
language, else `last_language`, else `preferred_locale`. `last_language` records
the most recently accepted turn's selected response language. UI changes never
translate existing content. Unsupported mock languages use a deterministic
fallback to `pt-BR` or `en` via the same conversation/UI chain; document mock
coverage in #24. Robust detection and broader language generation belong to
Epic #3; UI locale enums do not restrict future BCP 47 processing metadata.

## Errors and limits

Pre-stream failures return JSON with `Content-Type: application/json`:

```json
{"error":{"code":"CONVERSATION_NOT_FOUND","message":"Conversation not found."}}
```

`code` is stable; optional `message` is diagnostic text, never localized UI copy.
Optional `fields` contains field names and machine codes only, never input values.
The frontend maps codes to translation keys, with a generic unknown-code fallback.
Do not expose traces, SQL, identity existence or provider responses.

| HTTP | Codes | Meaning |
| --- | --- | --- |
| 400 | `INVALID_REQUEST`, `INVALID_CURSOR`, `OIDC_CALLBACK_INVALID` | Malformed JSON/query or invalid login transaction |
| 401 | `AUTH_REQUIRED`, `SESSION_EXPIRED` | Missing, expired or revoked session |
| 403 | `CSRF_INVALID`, `ORIGIN_FORBIDDEN` | Failed mutation security checks; never an ownership oracle |
| 404 | `CONVERSATION_NOT_FOUND` | Unknown, deleted or non-owned conversation |
| 409 | `IDEMPOTENCY_CONFLICT`, `MESSAGE_IN_PROGRESS`, `ATTEMPT_TERMINAL`, `CONVERSATION_BUSY` | Conflicting payload, duplicate active/terminal attempt or another active turn |
| 413 | `PAYLOAD_TOO_LARGE` | Body exceeds 64 KiB |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Mutation body is not JSON where required |
| 422 | `VALIDATION_ERROR` | Well-formed body/query violates schema or text limit |
| 429 | `RATE_LIMITED` | Per-user/IP limits; `Retry-After` seconds |
| 500 | `INTERNAL_ERROR` | Unexpected failure |
| 503 | `SERVICE_UNAVAILABLE` | Temporary dependency failure; optional `Retry-After` |

Reject unsupported SSE Accept values with 406 `NOT_ACCEPTABLE`. Validate the
session, origin/CSRF, owner, body and attempt before sending 200. After headers,
use [SSE errors](streaming.md), never pretend HTTP status can change.
One active attempt per conversation is a v1 limit. Numeric per-user/IP rate,
concurrency and server-output/time limits remain open for #20/#24; configure
finite bounds and test them before deployment. Logs exclude report text, tokens,
cookies, codes, CSRF values and raw cursors; use sanitized request IDs and codes.
Render message/profile text safely, never as trusted HTML. Session and owner
isolation apply to caches, database queries, streams and logging access.

## Decisions for follow-up

Resolved here: `/v1`, keyset pagination/order, wire DTOs, CSRF bootstrap,
non-disclosing 404, one active turn, terminal partial-message semantics and
no automatic regeneration on duplicate sends. #20 must select OIDC/session
libraries, storage and finite session timings; #21 must choose ORM/migrations,
physical deletion and retention; #24 must choose stream leases/checkpoint timing,
limits and mock language coverage. Production callback/ingress configuration and
backup/privacy policy require deployment review. These choices may refine this
design explicitly; they are not existing application behavior.
